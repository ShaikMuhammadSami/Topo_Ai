# CLOUD-V1-1A.4C2 — PostgreSQL authority separation and bootstrap contract v1

Status: source contract only; no live environment was changed. In particular,
this work did not read an RDS secret, connect to RDS, create a Kubernetes
Secret, run a live migration, or deploy a workload.

## Decision

TopoAI uses three PostgreSQL identities with separate lifecycles:

| Identity | Lifecycle | Authority |
| --- | --- | --- |
| RDS master | One-time/bootstrap and break-glass administration only | Creates the two dedicated roles with PostgreSQL's safe restricted-attribute defaults, converges supported mutable attributes, changes their passwords, removes inherited memberships, and establishes database/schema grants. It is never an application or migration credential. |
| `topo_migrator` | A controlled migration Job | Connects to the Topo database, has `USAGE, CREATE` on the `public` schema, owns the application objects it creates, runs Alembic DDL and migration-time DML, then reconciles application grants. |
| `topo_app` | Steady-state backend replicas | Connects and performs required application DML. It does not create or own schema objects and has no database, role, replication, or row-security-bypass authority. |

Pod lifecycle is not schema lifecycle. Backend Pods validate the current
Alembic revision, but never run `alembic upgrade head`. A bounded migration Job
uses `topo_migrator`; the Deployment uses only `topo_app`.

## Source-derived database capability inventory

Migrations `0001` through `0015` were re-read without modification. Together
they create, alter, and drop tables, indexes, foreign keys, unique/check
constraints, and migration metadata; several migrations also select, insert,
or update rows while transforming durable data. `0008` changes the width of
`alembic_version.version_num`. They do not create PostgreSQL extensions,
sequences, custom enum/types, functions, or triggers. The current 50-table ORM
metadata contains no server-generated sequence or identity default: string and
composite primary keys are generated by application code. Sequence authority
is nevertheless defined narrowly for a future Alembic-created identity or
sequence.

Steady-state repositories and services issue `SELECT`, `INSERT`, `UPDATE`, and
`DELETE`. Readiness issues a bounded `SELECT 1`. Normal startup only reads the
Alembic revision. Explicit developer schema-adoption tooling can perform DDL,
but it is not part of production startup and must not run with `topo_app`.

The golden keeps the existing public schema (`public`) assumption. Introducing a new
schema would require rewriting historical migrations and is not part of this
contract. The Topo database is dedicated to TopoAI; revoking broad `PUBLIC`
database/schema grants therefore does not displace an unrelated application.

## Exact privilege matrix

| Scope | `topo_app` | `topo_migrator` | RDS master |
| --- | --- | --- | --- |
| Database | `CONNECT`; explicitly no `CREATE` or `TEMPORARY` | `CONNECT`; explicitly no database `CREATE` or `TEMPORARY` | Bootstrap administration only |
| `public` schema | `USAGE`; no `CREATE`; no ownership | `USAGE, CREATE`; no schema ownership | Retains infrastructure ownership |
| Application tables | `SELECT, INSERT, UPDATE, DELETE`; no ownership, `TRUNCATE`, `REFERENCES`, or `TRIGGER` grant | Owns objects it creates and can apply the DDL/DML required by Alembic | Bootstrap/break-glass only |
| Sequences | `USAGE` only | Owns sequences it creates | Bootstrap/break-glass only |
| Application functions | No grant; `PUBLIC EXECUTE` is revoked for migrator-created/public-schema functions | Owns functions it creates | Bootstrap/break-glass only |
| `alembic_version` | `SELECT` only | Owns/manages it as Alembic metadata | Bootstrap/break-glass only |
| Role attributes | `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE INHERIT NOREPLICATION NOBYPASSRLS` | Same | RDS-managed |

Both dedicated roles have connection limit `-1`, no expiry, no per-role
configuration, and no inherited role memberships. Bootstrap explicitly
converges the mutable attributes that an RDS master can legally manage and
strictly verifies the complete final attribute tuple. For a newly created
ordinary role, PostgreSQL's safe defaults supply `NOSUPERUSER`,
`NOREPLICATION`, and `NOBYPASSRLS`; bootstrap verifies those catalog values
without issuing privileged attribute toggles. A pre-existing role with any of
those elevated attributes fails closed as
`DATABASE_ROLE_UNSAFE_ELEVATED_ATTRIBUTE` and requires human/admin
remediation. Bootstrap also fails closed if a dedicated role owns the database
or schema, or if `topo_app` owns an application object. It never transfers
object ownership to `topo_app`.

`PUBLIC` loses `CONNECT`, database `CREATE`/`TEMPORARY`, and schema `CREATE` on
the dedicated Topo database. The two roles receive only their direct grants.

## Future and existing objects

Default privileges are established **for objects subsequently created by
`topo_migrator` in `public`**:

- tables grant `SELECT, INSERT, UPDATE, DELETE` to `topo_app`;
- sequences grant `USAGE` to `topo_app`;
- functions grant nothing to `topo_app`, and their default `PUBLIC EXECUTE` is
  revoked.

PostgreSQL default privileges are not retroactive. Consequently every
migration Job performs this ordered lifecycle:

1. `python -m alembic -c /opt/topo/alembic.ini upgrade head`
2. `python /opt/topo-admin/topo_database_admin.py reconcile`

Reconciliation runs as exactly `topo_migrator`. It revokes and reapplies the
minimum application grants across existing public-schema tables and
sequences, removes application and public function execution, and finally
revokes all write/DDL-adjacent table privileges from `topo_app` on
`alembic_version` before granting `SELECT`. A failure in either command fails
the Job; the backend is not rolled out until the Job succeeds.

## Bootstrap utility and concurrency

[`scripts/cloud/topo_database_admin.py`](../../scripts/cloud/topo_database_admin.py)
has two modes:

- `bootstrap` reads seven mounted files, connects as the RDS master with
  `sslmode=require`, and converges role attributes, passwords, memberships,
  grants, defaults, and dedicated-role connectivity.
- `reconcile` reads the migration URL from `TOPO_DATABASE_URL`, requires
  `current_user = topo_migrator`, and reconciles future/default and existing
  object privileges after Alembic.

Identifiers are composed with `psycopg.sql.Identifier`. PostgreSQL role DDL
does not accept a password bind parameter, so the utility derives a
SCRAM-SHA-256 verifier through libpq and composes only that verifier with
`psycopg.sql.Literal`; the raw password is not put into SQL. Connection values
are supplied to Psycopg as values. Output is restricted to a fixed success or
fixed failure message: neither connection URLs, credentials, nor driver
exceptions are logged.

Bootstrap and reconciliation use separate session-level advisory locks.
Concurrent bootstrap attempts therefore cannot race role creation. A Job
timeout or lost client response is an **ambiguous outcome**, not proof that the
database was untouched. The correct retry is the same Job with the same
intended credentials. Catalog checks, `ALTER ROLE`, `REVOKE`, `GRANT`, default
privilege statements, and existing-object reconciliation are idempotent.

## Live-discovered RDS administrator compatibility repair

The first C2-B live bootstrap exposed an authority difference that the local
acceptance fixture had masked: that fixture ran bootstrap as a true PostgreSQL
superuser, while an AWS RDS master user is not a PostgreSQL superuser. The
original role DDL explicitly toggled `NOSUPERUSER`, `NOREPLICATION`, and
`NOBYPASSRLS`; PostgreSQL does not permit an ordinary RDS-style `CREATEROLE`
administrator to manage all of those restricted attributes.

Normal convergence now creates absent roles with `LOGIN`, relies on
PostgreSQL's safe ordinary-role defaults for the three restricted attributes,
then verifies their false values through `pg_roles`. Existing safe roles are
converged only across supported mutable properties. Existing roles with
`SUPERUSER`, `REPLICATION`, or `BYPASSRLS` fail closed before normal alteration.
The full final authority invariant remains unchanged.

This source repair has not been retried against live RDS. The read-only live
diagnostic established the failure boundary, but the real database must not be
described as bootstrapped until the guarded C2-B procedure is run again and its
postconditions are independently verified.

The script is mounted from the non-secret `topo-database-admin-scripts`
ConfigMap into the already accepted immutable backend image. The Secret volume
uses group-readable mode `0440` with Pod `fsGroup: 10001`, so the non-root
process can read it without making it world-readable. This avoids a
second admin image supply chain. Both Jobs are non-root, use a read-only root
filesystem, drop all capabilities, use `RuntimeDefault` seccomp, receive no
service-account token or Kubernetes permissions, and have a bounded deadline
and retry count.

## Database role material

[`scripts/cloud/generate_database_role_material.py`](../../scripts/cloud/generate_database_role_material.py)
creates two independent 48-byte-entropy URL-safe passwords with Python's
`secrets` module. It reuses the accepted A0 output-boundary helpers:

- output must resolve outside the Git worktree;
- existing files and symlinks are never overwritten;
- writes are exclusive and mode `0600` on POSIX;
- a partial failure removes only files created by that invocation;
- no password or URL is printed.

It emits exactly:

- `topo-app-password.txt`
- `topo-migrator-password.txt`
- `database-url.txt`
- `migration-database-url.txt`

The URLs are constructed with SQLAlchemy `URL.create`, so reserved characters
are escaped safely, and are parsed back before persistence. Both use the
driver-supported form `postgresql://<role>:<encoded-password>@<host>:<port>/<db>?sslmode=require`.
The runtime normalizes this to the Psycopg SQLAlchemy dialect internally. The
utility does not generate, fetch, or store the RDS master password.

## Temporary bootstrap Secret

The `topo-database-bootstrap` Secret is temporary and is not
`topo-backend-runtime`. It contains exactly these mounted-file keys:

1. `database-host`
2. `database-port`
3. `database-name`
4. `master-username`
5. `master-password`
6. `topo-app-password`
7. `topo-migrator-password`

It contains no Topo bootstrap API token, SecretStore keyring/root material,
AWS credential, or kubeconfig. Deleting the Job does not delete this Secret.
The human operator must delete it after bootstrap and dedicated-role checks.
AWS Secrets Manager retains the RDS-managed master secret as infrastructure
bootstrap/break-glass authority; that AWS-managed secret is not deleted.

The RDS master value must never be copied into `topo-backend-runtime`, a
Deployment, the migration Job, a ConfigMap, a command argument, an image, or a
log.

## Future C2-B operator procedure — do not execute in C2-A1

These steps are deliberately human-owned and use placeholders. Start from a
clean, reviewed checkout containing accepted immutable backend reference
`<BACKEND_IMAGE_REPOSITORY>@sha256:<BACKEND_DIGEST>`.

1. Authenticate using the approved SSO profile and verify account, ARN, region,
   EKS context, namespace `topo-system`, and the exact RDS master Secret ARN.
   `aws sts get-caller-identity --profile <SSO_PROFILE>` must show the expected
   production authority before proceeding.
2. Create a locked-down working directory outside `C:\Topo-ai`. Retrieve the
   RDS-managed Secret into that directory without printing it. Parse its
   `username` and `password` into separate files; never place either in shell
   history or command arguments. Record host, port, and database as separate
   non-secret files.
3. Generate the two dedicated credentials and validated TLS URLs without
   printing them:

   ```powershell
   Set-Location C:\Topo-ai
   & .\backend\.venv\Scripts\python.exe .\scripts\cloud\generate_database_role_material.py `
     --output-dir <SECURE_DIRECTORY_OUTSIDE_REPO> `
     --db-host <RDS_ENDPOINT> --db-port 5432 --db-name <DATABASE_NAME>
   ```

4. Materialize the reviewed script ConfigMap from source. Pin the Job's image
   to the accepted backend digest. Use `kubectl create configmap ...
   --from-file=topo_database_admin.py=... --dry-run=client -o yaml` and apply
   only the resulting non-secret object.
5. Construct `topo-database-bootstrap` with seven `--from-file` inputs matching
   the key contract above. Do not use `--from-literal` for a credential and do
   not save rendered Secret YAML.
6. Apply only `database-bootstrap-job.yaml`, wait for its bounded completion,
   and inspect its fixed-value logs. Job success includes direct
   `topo_migrator` and `topo_app` connectivity plus privilege-boundary checks.
7. If outcome is ambiguous, inspect Job/Pod status, then rerun with the same
   intended credentials; do not generate a second credential set merely due to
   timeout.
8. After success, delete the temporary Kubernetes Secret explicitly and verify
   it is absent. Delete/retain the completed Job and non-secret ConfigMap per
   the operational evidence policy. Do not delete the AWS-managed RDS master
   secret.
9. Preserve `topo-app-password.txt`, `topo-migrator-password.txt`,
   `database-url.txt`, and `migration-database-url.txt` in the approved secure
   handoff location for C2-C. Securely remove the temporary local copy of the
   RDS master JSON/password according to the operator's credential policy.

1. Reverify SSO identity, context, namespace, accepted backend digest, and that
   `topo-database-bootstrap` is absent.
2. Run the accepted A0 generator into a second secure directory outside Git to

3. Validate the two database URL files with the C2-A1 generator contract. The

4. Create `topo-backend-runtime` directly from files without rendering Secret

   `database-url`, `migration-database-url`, `bootstrap-token-hashes-json`,

5. Recreate the non-secret script ConfigMap from the reviewed source if it is
   absent. Pin `backend-migration-job.yaml` to the same accepted backend digest
   as the future Deployment.
6. Apply the migration Job. It must connect as `topo_migrator`, reach the exact
   accepted Alembic head `0015_security_audit`, and complete privilege
   reconciliation before succeeding.
7. Verify through bounded, non-secret checks that `topo_app` can connect,
   select/insert/update/delete application rows, and read
   `alembic_version`; it must fail to create/alter/drop schema objects or
   write migration metadata. Verify `topo_migrator` retains no admin role

8. Preserve `topo-backend-runtime` for C3. Remove local generated files under
   the approved secret-material retention procedure. Only after all checks pass
   may the backend Deployment be considered for a separate deployment block.

## Retry, rollback, and remaining validation

Bootstrap has convergence semantics, not transactional rollback across role
DDL and later connectivity tests. On an ambiguous failure, rerun the same
desired state. A failed migration must not be followed by backend rollout;
repair the migration issue, rerun Alembic as `topo_migrator`, and allow
reconciliation to finish. Never substitute the master URL as a workaround.

C2-A1 validates the source and, where locally available, PostgreSQL 16
privilege behavior. C2-B still must prove the one-time bootstrap against live
RDS. C2-C still must prove the exact Alembic head, runtime DML/DDL boundary, and
Secret wiring in the golden cluster. No live environment was changed by this
document or its accompanying implementation.
